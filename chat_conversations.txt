Core

The core directory contains all shared resources used across the application.

Core is not limited to infrastructure. Any reusable implementation that is shared between multiple modules belongs in core.

Examples:

Shared services
Shared hooks
Shared schemas
Shared UI components
Shared utilities
Shared types
Shared stores
Global providers

A resource should only be moved to core when it is genuinely reusable.

If a resource belongs to a single business module, it must remain inside that feature.

Features

Each feature represents a complete business module.

Pages

# 13. Important Rules & Gotchas

## ✅ DO

- Always use `apiService` for HTTP requests
- Keep business logic inside features
- Keep shared logic inside core
- Create sub-features for large domains
- Define query keys for every API module
- Use TypeScript strict mode
- Keep pages as composition layers
- Import UI exclusively from `@/core/ui`
- Use React Query for server state

---

## ❌ DON'T

- Don't import one feature into another feature
- Don't put business logic in pages
- Don't bypass `apiService`
- Don't use raw axios directly
- Don't move feature-specific code into core prematurely
- Don't expose sub-features publicly
- Don't use `any`
- Don't hardcode React Query keys

---

## ⚠️ Common Pitfalls

### Shared Code Too Early

Do not move code to `core` simply because it is used twice.

First evaluate whether the functionality truly belongs to multiple business domains.

### Feature Coupling

Features must remain independent.

Cross-feature imports create hidden dependencies and increase maintenance costs.

### Incorrect Ownership

A feature should own its business logic.

Only reusable, domain-independent code belongs in `core`.

### Query Key Inconsistency

Always define and use feature query key factories.

Never hardcode query keys inside components.
Module Export Rules

To keep imports predictable and maintainable, the project follows strict export conventions.
